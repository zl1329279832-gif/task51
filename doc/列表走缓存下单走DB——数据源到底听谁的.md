# 列表走缓存、下单走 DB——数据源到底听谁的

> 写给接入方：别被"列表页显示还有货，点进去就结束"搞懵，这套设计是故意的。


## 一句话总结

| 操作 | 数据源 | 原因 |
|------|--------|------|
| `findAll`（列表页） | Redis 缓存优先，miss 了才回 DB | 刷列表的人多、容忍度高，扛流量用 |
| `exportSeckillUrl`（点"立即秒杀"按钮） | **直接查 DB** | 决定用户能不能下单，必须实时 |


## 为什么数据源不一样

`SeckillServiceImpl.findAll()` 先读 Redis Hash（key 固定是 `"seckill"`），没命中才查 DB 再回写缓存。
这个接口的调用场景是首页列表——几十上百人同时刷，数据晚几秒不影响体验，关键是别把 DB 打挂。

`exportSeckillUrl(long seckillId)` 完全不同：它要判断"活动是否已开始/已结束"、"库存是否归零"，
然后才决定要不要把真正的秒杀地址（带 MD5 签名）吐给前端。
这一步如果读缓存，就可能出现"活动已结束但缓存里还显示有库存"的问题，用户拿到地址也下不了单，白跑一趟。
所以这里**每次都穿透到 DB**，顺便把缓存也刷新一下。


## 缓存 TTL 60 秒，窗口里会出什么"不一致"

缓存过期时间是 `CACHE_TTL_SECONDS = 60`，也就是最坏情况下列表页的数据比 DB 慢 60 秒。
这段时间内你可能遇到：

1. **库存看着还有，点进去就没了**
   列表页展示的是缓存里的 `stockCount`，但实际库存已经被别人下单扣掉了。
   用户点"立即秒杀"→ 调 `exportSeckillUrl` → 查 DB 发现 `stockCount <= 0` → 返回未开启。
   **这不是 bug，是预期行为。**

2. **活动看着还没开始，其实已经开始了**
   列表里的 `startTime` 是从缓存读的，不影响判断，但如果恰好在这 60 秒内运营改了活动时间（DB 改了），
   列表页看不出来。`exportSeckillUrl` 会以 DB 为准，正确放行或拦截。

3. **活动看着还在进行，其实已经结束了**
   和第 1 条同理，`endTime` 已过但缓存还没刷，列表仍显示"进行中"。
   真正进入下单流程时，`exportSeckillUrl` 会拦掉。

**结论：列表页是"信息展示"，不是"准入凭证"。真正的准入判断都在 `exportSeckillUrl` 和 `executeSeckill`，这俩都读 DB。**


## 缓存什么时候会被刷新

不是只有 TTL 到期才会刷新，以下操作都会主动更新缓存里的 Seckill 对象并重置 60 秒 TTL：

- `findAll()`：缓存 miss 时，全量从 DB 加载并写入。
- `exportSeckillUrl()`：每次调用都拿 DB 数据覆盖缓存。
- `findById()`：缓存 miss 时写入。
- `executeSeckill()`：下单成功后（库存 -1），把最新的 Seckill 对象写回缓存。

所以在高并发场景下，热门商品的缓存几乎不会真正过期——不断有人点进去，就不断被刷新。
真正可能"过期"的是那些没人访问的冷门商品。


## 接入方该怎么用

- 前端列表页直接调 `findAll`，拿到的数据用来展示，**不要用来做按钮状态判断**。
- "立即秒杀"按钮是否可点击，以 `exportSeckillUrl` 返回的 `Exposer.exposed` 字段为准。
- 如果列表页显示"有货"但 `exportSeckillUrl` 说"未开启"，前端正常展示"活动未开始/已结束"即可，不要弹错误提示。
