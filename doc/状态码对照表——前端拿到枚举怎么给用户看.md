# 状态码对照表——前端拿到枚举怎么给用户看

> SeckillStatEnum 是服务端的内部状态码，SeckillController 返回给前端的文案不完全是枚举的 `stateInfo`，
> 这张表帮你把对应关系一次理清楚。


## SeckillStatEnum 原始定义

| 枚举常量 | state (int) | stateInfo (String) |
|---------|-------------|-------------------|
| `SUCCESS` | 1 | 秒杀成功 |
| `END` | 0 | 秒杀结束 |
| `REPEAT_KILL` | -1 | 重复秒杀 |
| `INNER_ERROR` | -2 | 系统异常 |
| `DATA_REWRITE` | -3 | 数据串改（注：代码里写的是"串改"，应该是"篡改"的笔误） |


## 实际返回对照表

下面是 `POST /seckill/{seckillId}/{md5}/execution` 接口在不同情况下**真正返回给前端的内容**。

注意：这个接口的返回结构是 `SeckillResult<SeckillExecution>`，外层有 `success` 字段，内层 `SeckillExecution` 有 `state` 和 `stateInfo`。

### 正常业务流程（外层 success = true）

| 场景 | 异常类型 | SeckillExecution.state | SeckillExecution.stateInfo | 前端建议处理 |
|------|----------|----------------------|--------------------------|-------------|
| 下单成功，库存扣了，订单写了 | 无异常 | **1** | 秒杀成功 | 跳转订单详情页，展示恭喜 |
| 重复下单（同一用户同一活动再来一次） | `RepeatKillException` | **-1** | 重复秒杀 | 提示"您已经参与过本次活动" |
| 活动已结束（库存为 0 或时间已过） | `SeckillCloseException` | **0** | 秒杀结束 | 提示"活动已结束"，关闭秒杀弹窗 |
| 其他未预期错误 | `SeckillException` | **-2** | 系统异常 | 通用错误提示，引导用户重试或联系客服 |

### 前置校验失败（外层 success = false）

这些情况根本不会走到 `SeckillExecution`，直接被 Controller 层拦掉了：

| 场景 | SeckillResult.success | SeckillResult.error | 前端建议处理 |
|------|----------------------|--------------------|----|
| Cookie 里没有 `killPhone` | false | `"未注册"` | 引导用户先注册/登录 |
| 调用 `exposer` 或 `execution` 时抛了未知异常 | false | 异常 message | 通用错误提示 |

### exposer 接口的返回（单独说一下）

`POST /seckill/{seckillId}/exposer` 返回的是 `SeckillResult<Exposer>`，结构和 execution 不同：

| 场景 | SeckillResult.success | Exposer.exposed | Exposer 其他字段 | 前端建议处理 |
|------|----------------------|-----------------|-----------------|----|
| 活动可参与，返回秒杀地址 | true | true | `md5`, `seckillId` | 用 md5 拼 execution 请求，展示秒杀按钮 |
| 活动未开始 | true | false | `startTime`, `endTime`, `now`, `seckillId` | 展示倒计时，按钮置灰 |
| 活动已结束 | true | false | `startTime`, `endTime`, `now`, `seckillId` | 展示"活动已结束" |
| 库存不足 | true | false | `startTime`, `endTime`, `now`, `seckillId` | 展示"已抢光" |
| 活动不存在 | true | false | 只有 `seckillId` | 提示活动不存在 |
| 接口异常 | false | — | 错误信息在 SeckillResult.error | 通用错误提示 |


## 前端接入备忘录

1. **先判断 `SeckillResult.success`**：false 的时候直接看 `error` 字段，不要往 `data` 里找了。
2. **success = true 再看 `data.state`**：1 是成功，0 是结束，-1 是重复，-2 是系统异常。
3. **`DATA_REWRITE`（-3）在执行接口里不会出现**：这个枚举值目前代码里没有地方会用到，但留着扩展，前端可以先不用管。
4. **stateInfo 可以直接展示给用户看**，但建议前端自己做一层映射——万一以后服务端文案改了（比如修那个"数据串改"的 typo），前端不用跟着改。
