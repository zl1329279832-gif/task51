# 预约提醒子系统——别把它当秒杀用

> 写给接入方：预约 ≠ 抢到，提醒 ≠ 下单，这套接口只负责"到点喊你"。


## 先搞清楚一件事

`ReservationController` 下的四个接口，做的事情只有一件：
**让用户在活动开始前登记手机号，活动开始后拉取"该去抢了"的提醒。**

它 **不参与库存扣减**，**不生成订单**，**不保证你能买到**。
用户拿到提醒后，还是得老老实实调 `SeckillController` 的 `executeSeckill` 才能真正下单。

把预约当秒杀用的想法，趁早打消。


## 四个接口都是干嘛的

| 接口 | 方法 | 干啥 |
|------|------|------|
| `POST /seckill/reservation/{seckillId}/reserve` | `reserve` | 预约：活动还没开始才能约，约好了存在 `seckill_reservation` 表里 |
| `DELETE /seckill/reservation/{seckillId}/cancel` | `cancel` | 取消：活动没结束才能取消，删掉记录 |
| `GET /seckill/reservation/my` | `myReservations` | 我的预约列表：自动过滤掉已结束的活动，只展示还活着的预约 |
| `GET /seckill/reservation/{seckillId}/reminders` | `pullReminders` | 拉取提醒：活动进行中才能拉，拉过就标记已消费 |


## 预约的前置条件

`reserve` 不是什么时候都能调的，规则如下：

- **活动还没开始（`now < startTime`）**：允许预约。
- **活动已开始（`startTime ≤ now ≤ endTime`）**：不允许，都开始了你还预约啥，直接去抢。
- **活动已结束（`now > endTime`）**：不允许，结束了就别想了。

同时：
- 必须在 Cookie 里带上 `killPhone`（用户手机号），否则返回 `"未注册"`。
- 同一个用户同一个活动不能重复预约：Redis Set 里先判一次（快），DB 的唯一索引 `uk_seckill_user` 再兜底一次（稳）。
- DB 用的是 `INSERT IGNORE`，即使并发穿透也不会报唯一键冲突。


## pullReminders 的时间窗

`pullReminders` 是这套系统里最容易被误用的接口，重点说一下。

**只有在活动进行中（`startTime ≤ now ≤ endTime`）才能拉到数据。**

- 活动还没开始：拉不到，这时候还没到"提醒你去抢"的时候。
- 活动已结束：拉不到，过了这村没这店。

前端如果想做"到点自动弹提醒"，正确的做法是：
1. 先用 `/seckill/time/now` 拿到服务器当前时间。
2. 判断 `startTime ≤ now ≤ endTime`。
3. 满足条件再调 `pullReminders`。


## pullReminders 的幂等规则

这个接口**设计上是幂等的**——同一个用户对同一个活动的提醒，拉一次就没了。

实现方式：
- `seckill_reservation` 表有个 `status` 字段，`0 = 待提醒`，`1 = 已提醒`。
- `pullReminders` 查出所有 `status = 0` 的记录，返回给调用方，然后在**同一个 `@Transactional` 事务里**把这些记录的 `status` 改成 `1`。
- 第二次调用的时候，`status = 0` 的记录已经没有了，返回空列表。

这意味着：
- 客户端可以放心重试——不会因为网络抖动导致"提醒被消费了两次"。
- 但要注意，**第一次拉到数据的那次请求必须成功响应给客户端**，如果这次请求在网络层丢了，提醒就"被消费但没被看到"。
  建议客户端拿到提醒数据后先落盘/展示，再认为消费成功。


## 取消预约的限制

`cancel` 在活动结束后不允许调用——不是技术限制，是业务上没必要了。
如果用户网络慢、在活动结束前最后一秒发了取消请求，服务端判断 `now > endTime` 会直接拒绝，返回异常信息。


## 和 executeSeckill 的关系（重要，画重点）

```
用户预约 → 到点拉提醒 → 看到提醒 → 去秒杀页面 → 调 exportSeckillUrl → 调 executeSeckill → 下单成功
    ↑                           ↑
    预约子系统管到这里            这往后是 SeckillController 的事
```

预约提醒 **不会** 帮你：
- 锁定库存
- 跳过 MD5 校验
- 跳过防重复下单检查

它就是个闹钟，仅此而已。


## Redis 在预约里的角色

- Redis Set（key 格式 `seckill:reservation:{seckillId}`）只做**快速查重**，不存业务状态。
- 真正的数据权威在 DB 的 `seckill_reservation` 表。
- 这个 Redis Set **没有设置 TTL**——如果活动结束后不再需要，可以考虑清理，但目前代码里没有自动清理逻辑。
